    MCP 2025-11-25 · 2026-07-28 OpenAPI 3.1.1 · 3.2.0 RFC 9110 family

    The three specs behind every tool mcpgp generates

    A course through MCP, OpenAPI and HTTP, limited to what a generator of MCP servers from OpenAPI contracts needs. Every lesson links to the exact section of the official text, says why it matters for mcpgp, and points to the code or doc in this repo where it shows up. Tick lessons off as you go; progress stays in this browser.

    About 19 hours in total. If time is short, do the lessons marked core first (about 7 hours).

    Found while building this course

    MCP published revision 2026-07-28, and the runtime negotiates at most 2025-11-25. It is a large change: sessions and the initialize handshake are gone, server-to-client requests are replaced by Multi Round-Trip Requests, tasks moved into an extension, and Roots, Sampling and Logging are deprecated. ADR-0013 says each runtime supports the newest revision, so mcpgp is now outside its own policy. Module 2 covers what this means for confirmations, toolsets and progress.

    Module 030 min

    How to read specs

    Three habits that make long standards readable.

    0.1Normative words and how specs are layered

    20 min · core

    Every spec in this course uses MUST, SHOULD and MAY with a defined meaning. A MUST is a conformance requirement; a SHOULD is a requirement you may skip only with a reason. When you decide what mcpgp has to do, this is the vocabulary that settles arguments.

    Read

    • RFC 2119 and RFC 8174Both are one page. 8174 adds that only UPPERCASE words carry the meaning.
    • RFC 9110 §1 IntroductionHow the HTTP specs are split: semantics (9110), caching (9111), each wire version (9112, 9113, 9114).
    • MCP 2025-11-25, OverviewThe map of the MCP spec: base protocol, server features, client features, utilities.

    Key points

    • Read the data types and the error sections first; the prose in between explains them.
    • Every MCP revision has a changelog page. When a new revision appears, start there.
    • The MCP schema reference is the normative source for field names; the prose pages are examples around it.

    0.2Where mcpgp already wrote its decisions down

    10 min

    Most lessons end with "in mcpgp". These are the documents they point to; skim them once so the references land.

    Read

    • docs/spec/tools-contract.mdWhat an agent receives. The main document this course is checked against.
    • ADR-0006 and ADR-0013Input grouping by location, and which MCP revisions a runtime supports.
    • docs/spec/compatibility.mdThe compatibility matrix that should change whenever this course finds a gap.
    Module 1about 6 h

    MCP 2025-11-25: what the runtime speaks today

    The revision mcpgp implements. Learn it well first; Module 2 is easier as a diff against it.

    1.1Base protocol: JSON-RPC, _meta, JSON Schema usage

    30 min · core

    Every message mcpgp sends is a JSON-RPC 2.0 message. The base page also fixes which JSON Schema dialect tool schemas use, which decides how the compiler must shape them.

    Read

    • Basic, OverviewMessages (requests, results, errors, notifications), _meta key naming, and the section "JSON Schema Usage" (#json-schema-usage).
    • ArchitectureHost, client, server; capability negotiation as the central idea.
    • JSON-RPC 2.0§5.1 error object and the reserved codes (-32700 to -32603).

    Key points

    • Schemas without $schema are JSON Schema 2020-12. OpenAPI 3.0 schemas are not, so the compiler must convert them.
    • _meta keys use a reverse-DNS prefix. Yours are mcpgp/…; MCP reserves io.modelcontextprotocol/.

    In mcpgp

    Result _meta (mcpgp/instance, mcpgp/correlationId) is in tools-contract §6.

    1.2Lifecycle and version negotiation

    25 min · core

    The runtime accepts four revisions. Negotiation decides which features are allowed on a connection, which is how ADR-0013 gates features "per negotiated revision".

    Read

    • LifecycleInitialization, version negotiation, capability negotiation, shutdown, timeouts.

    Key points

    • The client proposes a version; the server answers with that one or another it supports. The client disconnects if it can't use the answer.
    • Capabilities are declared once, at initialization. A feature the client did not declare (elicitation, for example) must not be used.

    In mcpgp

    The revisions the runtime knows are string literals in runtime/ ("2025-11-25", "2025-06-18", "2025-03-26", "2024-11-05"). Capabilities are built in McpServerFactory.

    Check yourself
    1. A client declares no elicitation capability and calls a destructive tool. What must mcpgp do?Use the token fallback: return CONFIRMATION_REQUIRED with a confirm token (tools-contract §8). Sending elicitation/create would break the negotiated capabilities.

    1.3Transports: stdio and Streamable HTTP

    40 min · core

    Customers run the server either as a local process (stdio, the desktop bundle) or as an HTTP service. The HTTP rules (sessions, Origin, SSE streams) decide what progress and elicitation can do.

    Read

    • Transportsstdio (stdout carries only MCP messages, logs go to stderr); Streamable HTTP: POST and GET, SSE, session management (Mcp-Session-Id), resumability, the MCP-Protocol-Version header, the security warning about Origin.

    Key points

    • On HTTP, servers must validate Origin to block DNS rebinding, and should bind to localhost when local.
    • Sessions are optional. Without them (stateless), the server can't send progress or requests outside a response stream.

    In mcpgp

    StdioTransport.java (drain on EOF) and http/HttpServerConfiguration.java. tools-contract §14.3 already notes progress is unavailable on stateless HTTP.

    1.4Tools, in depth

    60 min · core

    This page is the product surface. Read every line, then compare it with what the compiler emits.

    Read

    • Server → ToolsData types: Tool, tool names (#tool-names), Tool Result, resource links, structured content (#structured-content), output schema (#output-schema), error handling (#error-handling), security considerations.
    • Schema → ToolAnnotationsThe exact meaning and defaults of readOnlyHint, destructiveHint, idempotentHint, openWorldHint.

    Key points

    • If a tool declares outputSchema, the server MUST return conforming structuredContent, and SHOULD also return the JSON as text for older clients.
    • In 2025-11-25, structuredContent is an object, so an array response needs wrapping. (2026-07-28 allows any JSON value; see 2.6.)
    • Input validation failures are tool results with isError: true, not protocol errors, so the model can correct itself.
    • Annotations are hints. Clients must treat them as untrusted unless the server is trusted.
    • execution.taskSupport is new in this revision (lesson 1.8).

    In mcpgp

    ManifestWriter.java:426 writes outputSchema as null for every tool. That is the biggest gap this lesson exposes. Annotation defaults per method: tools-contract §5.

    Check yourself
    1. An upstream API returns 422 with a list of invalid fields. Protocol error or tool error?Tool error (isError: true) with the field list in the text, so the model can fix the arguments. Protocol errors are for unknown tools and malformed requests.
    2. Why should a GET tool keep openWorldHint: true?Because it talks to an external system whose data is outside the server's control, which is what the hint describes. It is unrelated to safety.

    1.5Resources, prompts and completion

    45 min

    Read

    In mcpgp

    1.6Utilities: cancellation, progress, pagination, logging

    40 min · core

    Small pages with large effects. Cancellation in particular has no implementation in mcpgp yet.

    Read

    • Cancellationnotifications/cancelled, race conditions, what the receiver should stop.
    • ProgressprogressToken, increasing progress, optional total.
    • PaginationOpaque cursors on list operations, including tools/list.
    • Loggingnotifications/message and setLevel. Deprecated in 2026-07-28; read it only to understand that change.

    In mcpgp

    1.7Elicitation: form mode and URL mode

    45 min · core

    Confirmations of destructive calls already use form mode. URL mode (new in this revision) is the standard way to sign each user in to the downstream API, which the roadmap lists as deferred.

    Read

    • ElicitationForm mode and its restricted schema (flat objects of primitives); URL mode; response actions accept / decline / cancel; "URL Mode Elicitation for OAuth Flows"; the URLElicitationRequiredError (-32042); the phishing section.

    Key points

    • Form mode MUST NOT ask for passwords, keys or tokens. Those go through URL mode, so the client never sees them.
    • URL mode for third-party OAuth makes the server an OAuth client of the upstream. It must bind the tokens to the user's identity (the sub from MCP authorization), never to the session alone.
    • Asking for a missing required argument through form mode fits only when the argument is a flat primitive.

    In mcpgp

    runtime/…/mcp/Confirmations.java; tools-contract §8. In 2026-07-28 these requests move into MRTR (lesson 2.4).

    Check yourself
    1. Why can't mcpgp ask the user for an upstream API key through form mode?The spec forbids sensitive data in form mode; it would pass through the client and possibly the model. URL mode keeps it between the user's browser and the server.

    1.8Tasks (experimental in 2025-11-25)

    40 min

    The natural fit for APIs that answer 202 Accepted and finish later. Read it to understand the model; the shape changed again in 2026-07-28 (lesson 2.7), so don't build against this version.

    Read

    • TasksCapabilities, tool-level negotiation (execution.taskSupport), task status lifecycle, TTL, the security section on binding tasks to an authorization context.

    In mcpgp

    Not used. A 202 with Location (lesson 4.4) maps to "working" until polling the status URL says done.

    1.9Authorization and security best practices

    50 min

    mcpgp is an OAuth resource server for HTTP deployments. The best-practices page also explains why token passthrough is forbidden, which constrains how downstream credentials may work.

    Read

    • AuthorizationProtected resource metadata (RFC 9728), resource indicators (RFC 8707), audience validation, Client ID Metadata Documents.
    • Security best practicesConfused deputy, token passthrough, session hijacking, SSRF.
    • RFC 9728§2 and §3: the metadata document and where it lives.

    In mcpgp

    docs/spec/auth.md and ADR-0005 (downstream auth per instance, which avoids passthrough by design).

    2.1Changelog and the deprecation registry

    30 min · core

    The fastest way to see the whole change. Do this lesson even if you skip the rest of the module.

    Read

    • 2026-07-28 Key ChangesNine major changes, twelve minor, four deprecations.
    • Deprecated features registryRoots, Sampling, Logging and Dynamic Client Registration; earliest removal in the first revision on or after 2027-07-28.
    ChangeEffect on mcpgp
    No sessions, no initializeConfirm tokens are bound to "the MCP session" (tools-contract §8); they need another binding, such as the authenticated user or a server-minted handle.
    List results must not vary per connectiontoolsets exposure changes tools/list per session (Toolsets.java). That is no longer allowed.
    MRTR replaces server-to-client requestsConfirmation through elicitation becomes an input_required result plus a retry.
    Logging deprecatedDon't build the logging gap from the board; use stderr and OTLP, which exist.
    Resource not found becomes -32602tools-contract §14.1 says -32002; gate it per revision.
    x-mcp-headerinstance could be mirrored into a header so gateways can route by instance.
    structuredContent may be any JSON valueArray responses don't need wrapping on this revision.

    2.2Stateless requests, versioning and server/discover

    35 min · core

    Each request now carries its own protocol version and client capabilities in _meta, and servers must answer server/discover. The adapter layer from ADR-0013 needs a second era.

    Read

    • Basic, OverviewRequest _meta fields, error code allocation (#error-codes), $ref resolution (#ref-resolution).
    • VersioningNegotiation without a handshake, and backward compatibility with initialization-based versions.
    • server/discover

    2.3Streamable HTTP, rewritten

    40 min · core

    No GET stream, no sessions, no resumability. New required headers mirror body fields so gateways can route without parsing JSON.

    Read

    • Streamable HTTPRequest Metadata (Mcp-Method, Mcp-Name), "Custom Headers from Tool Parameters" (x-mcp-header, its constraints, Base64 sentinel encoding), Server Validation (HeaderMismatch -32020), Cancellation (closing the stream cancels), Backward Compatibility.
    • stdioWhere notifications/cancelled still applies.

    Key points

    • x-mcp-header may only sit on string, integer or boolean properties reachable through properties alone. mcpgp's grouped inputs (query.region) qualify, because nesting through properties is allowed.
    • Never put secrets behind x-mcp-header; intermediaries see headers.
    • On HTTP, a closed response stream is the cancellation, which makes aborting the upstream call easier to wire.

    2.4Multi Round-Trip Requests (MRTR)

    35 min · core

    The replacement for elicitation/create sent by the server. mcpgp's confirmation flow already works almost like this (token, then call again), so the change may be a simplification.

    Read

    • Multi Round-Trip RequestsInputRequests, InputResponses, InputRequiredResult, requestState, Server Requirements (integrity protection and replay limits), Security Considerations.

    Key points

    • requestState comes back from the client, so it is attacker-controlled. If it affects anything that matters, protect it with an HMAC or AEAD and bind it to the user, the request and a short expiry.
    • Those are the same rules mcpgp's confirm tokens already follow (bound to tool, instance, argument hash; 5-minute expiry; single use).
    Check yourself
    1. MRTR alone doesn't guarantee single use. Where must mcpgp still enforce it?Server-side, as today: remember used confirm tokens until they expire. The spec says so explicitly for one-time redemptions.

    2.5Subscriptions and caching

    25 min

    Change notifications move to one subscriptions/listen stream, and list results carry cache hints.

    Read

    • Subscriptions
    • CachingttlMs and cacheScope on tools/list, resources/list and others.

    In mcpgp

    A built server's tool list only changes on restart, or on reload for resources, so a long ttlMs with scope private is honest. Return tools in a fixed order (the spec now says SHOULD); the manifest order already is one.

    2.6Tools in 2026-07-28

    30 min · core

    Same page as 1.4, with changes that touch the compiler directly.

    Read

    • Server → Tools"Input Required Tool Results", #x-mcp-header, Structured Content (any JSON value), the array output schema example, "Stateful Tools" (handles instead of sessions).

    Key points

    • Schemas may use any 2020-12 keyword; clients must follow the $ref resolution rules. mcpgp's $defs output fits.
    • "Stateful Tools" recommends returning a handle and accepting it later. It reads like a description of OpenAPI links (lesson 3.5).

    2.7Extensions: tasks, auth, MCP Apps

    35 min

    Extensions are where new features now arrive. Two of them touch mcpgp directly.

    Read

    • Extensions overview and client support matrixWhich clients support which extension; check this before building on one.
    • Tasks extensionPolling with tasks/get, tasks/update for input, no blocking tasks/result.
    • OAuth Client Credentials and Enterprise-Managed AuthorizationMachine clients and company identity providers, which match how customers run mcpgp.
    • MCP AppsInteractive UI from servers. Low priority for an API proxy; read the overview only.

    4.6Rate limits and retries

    30 min

    mcpgp never retries by itself, so the agent needs the signals. Both relevant headers are still drafts; know their status before depending on them.

    Read

    • RateLimit header fields (draft-11)Active draft in the httpapi working group, not an RFC. Defines RateLimit and RateLimit-Policy.
    • Idempotency-Key header (draft-07)Expired, not an RFC. Still widely used (Stripe and many payment APIs), so support it as an opt-in rule, not as a standard.
    Correction to the board

    The board lists Idempotency-Key as an IETF draft; the draft has since expired. The value for agents is unchanged, but treat it as a common convention that APIs opt into.
